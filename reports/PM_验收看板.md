## 零、每轮开工前的「对齐门禁」（固定流程，不可跳过）

**为什么需要**：两台机器之间的指令靠人工拷贝粘贴，格式/段落/数字极易丢失或截断。
如果对面按"它以为的结论"开工，跑完才发现前提不一致，整轮算力就白费。

### 流程

```
① PM 下发「对齐清单」——列出上一轮的关键数字（不给答案，只给问题）
② 对面**凭本地结果复述**这些数字（不许说"同意/收到"，必须报具体数值）
③ 双方 diff：
   · 全部一致 → 放行，接受本轮新任务
   · 任一不一致 → 停下，先解释差异来源（是拷贝丢了？还是实现不同？还是我记错了？）
④ 对齐通过后，才下发新任务指令
```

### 铁律

| # | 规则 |
|---|---|
| 1 | **只回答"一致"不算通过**——必须复述具体数字，让 PM 能核对 |
| 2 | 不一致时，**不许开始新任务**，先对齐 |
| 3 | 若差异来自 PM 记错，PM 必须认错并更正看板 |
| 4 | 每轮对齐结果记录在案（哪条不一致、如何解决） |

## 零之二、通讯格式规程（2026-10-18 起，双向适用）

**问题**：两台机器之间靠人工拷贝，散文式汇报容易丢格式、丢段落、丢括号里的关键值。

### 规程（PM 与实现方都必须遵守）

| # | 规则 |
|---|---|
| **F1** | 对齐清单必须是**一张表**，列固定为：`# / 项目 / PM 答案 / 你的答案 / 一致?` |
| **F2** | 实现方**填完后原样贴回整张表**——不改表结构、不删行、不加散文 |
| **F3** | 表中 `★` 标记的项，**PM 答案列留空（—）**，由实现方提供真实数据（防抄录式附和） |
| **F4** | 表格首尾各加一行 `<<<R1-BEGIN>>>` / `<<<R1-END>>>` 标记，便于判断是否被截断 |
| **F5** | 结论只写在表尾固定 3 行：`总项数 / 不一致数 / 结论`，不再另起一段 |
| **F6** | 结果汇报（非对齐）也统一用表：`任务 / 做了什么 / 关键数字 / 是否通过 / 产出文件` |
| **F7** | 数字必须带单位与口径指纹；缺失写 `无`，禁止留空或猜 |

### 填表纪律

> **先填「你的答案」，再看「PM 答案」。**
> 两者不同就保留你的答案——**不要改成我的**。
> 差异本身是最有价值的信息（可能是拷贝截断、实现不同、或 PM 记错）。

### 格式冻结条款（2026-10-18 用户确认）

> **F1–F7 格式已定版冻结。PM 不得单方面修改。**
> 若 PM 发现格式问题（如表格在聊天窗口折行丢列、★ 项被编造、项数膨胀），
> 必须先向用户说明问题与备选方案，经用户确认后才可调整。

## 零之三、交付验证规则（2026-10-18 新增，血的教训）

**事件**：实现方报告 3 个提交（cacd6be / 67fbc96 / 4540c0e）与 9 个产出文件，
PM 侧核实发现**全部不在 GitHub**——它的"已提交"只是本地 commit，从未 push。

### 规则（硬性）

| # | 规则 |
|---|---|
| **D1** | **"committed" ≠ "delivered"**。只有 git ls-remote origin master 能看到的 hash，才算交付 |
| **D2** | 每轮结束时，实现方必须自证：git ls-remote origin master 的 hash == 本地 git rev-parse HEAD，并把两个 hash 一起报出来 |
| **D3** | PM **不做无产物的判读**：声称产出的文件必须能在 pull 后的工作区找到，否则一律打回 |
| **D4** | 关键数字（夏普/净超额/回撤）必须能追溯到具体 JSON 文件与字段，不接受纯文字汇报 |
| **D5** | push 失败的，把错误原文贴回，不许用"已完成"掩盖 |

### 教训

PM 本轮接受了对面的文字汇报并据此下判读（P0 4/4、轨道 A 0/39、B1 门禁），
**全部无法验证**。这与之前"接受因子有效但没做 holdout"是同一类错误：
**把描述当成了事实。**

## 零之四、文件所有权与冲突协议（2026-10-18 新增）

**问题**：两台机器共用同一仓库，双方改同一文件会导致 push 被拒 + 需人工解冲突。

### 文件所有权（单写者原则）

| 目录/文件 | 唯一写者 | 说明 |
|---|---|---|
| eports/PM_验收看板.md | **PM（本机）** | 实现方只读，不得修改 |
| docs/*.md（设计稿/口径） | **PM（本机）** | 实现方可提建议，由 PM 落笔 |
| eports/R*_任务书.md | **PM（本机）** | 实现方只读执行 |
| eports/R*_对齐确认表.md | PM 建表 → **实现方只填「你的答案」列** | 不改结构、不加行、不删行 |
| actors/FACTOR_FALSIFICATION_LOG.md | **实现方（对面）** | PM 只读；PM 要加的结论写进看板 |
| actors/*.py、scripts/*.py | **实现方** | PM 不直接改 |
| config/*.yaml（除 backtest_window.yaml） | **实现方** | 成本/参数配置 |
| config/backtest_window.yaml | **PM** | 窗口口径 |
| eports/*.json、logs/* | **实现方** | 实验结果 |

### 冲突处理协议

| # | 场景 | 做法 |
|---|---|---|
| **C1** | push 被拒（non-fast-forward） | git pull --no-rebase origin master，**不许** --rebase（会改写历史） |
| **C2** | FACTOR_FALSIFICATION_LOG.md 冲突 | .gitattributes 已设 merge=union → **自动保留双方**，无需人工 |
| **C3** | 单写者文件冲突 | 以**所有者版本为准**，非所有者一方回退自己的改动 |
| **C4** | R*_对齐确认表.md 冲突 | 实现方回退，重新 git pull 后在最新版上填 |
| **C5** | 解完冲突必须验证 | git status 无未合并文件 + git ls-remote origin master == 本地 HEAD |

### 禁止

- ❌ 禁止 git push --force（会抹掉对方提交）
- ❌ 禁止 git pull --rebase（改写历史，两台机器会互相踢）
- ❌ 禁止在未 pull 的情况下修改单写者文件

## 零之五、交付台账与自动校验（2026-10-18 新增）

**问题**：靠对方"自报已提交"不可靠——实践已证明两次（对面 3 个提交全未推送；PM 自己也漏推过 1 次）。

### 机制

| 组件 | 文件 | 作用 |
|---|---|---|
| **台账** | eports/delivery_manifest.json | 声明每轮期望在 GitHub 出现的文件、最小字节、必须包含的提交/关键词 |
| **校验器** | scripts/pm/check_delivery.py | **直接查 origin/master 的树**（git plumbing），不读工作区、不看自报 |

### 校验器查什么

| 检查 | 方法 |
|---|---|
| 提交是否已在远端 | git merge-base --is-ancestor <hash> origin/master |
| 文件是否存在 | git cat-file -e origin/master:<path> |
| 文件是否够大 | git cat-file -s 对比台账 min_bytes |
| 内容是否达标 | git show origin/master:<path> 关键词匹配 |
| 单写者文件是否被篡改 | 远端 sha256 vs 本地工作区 sha256 |

### PM 每轮必做（新增第 ⑤ 步，取代"信任自报"）

`ash
# 等对方推送期间可以轮询
python scripts\pm\check_delivery.py --round R2 --watch 600

# 或一次性检查全部轮次
python scripts\pm\check_delivery.py
`

| 退出码 | 含义 | PM 动作 |
|---|---|---|
| 0 | 该轮交付完整 | 进入判读 |
| 1 | 有缺失 | **不打回判读**，按缺失清单要求补推 |

### 已抓到的两次真实案例

| 案例 | 对象 | 结果 |
|---|---|---|
| C1 | 实现方 | 3 个提交（cacd6be/67fbc96/4540c0e）全部未推送 |
| C2 | **PM 本人** | R2_任务书 提交 62fe820 漏推，被校验器在同一小时内抓出 |

> **结论**：这个机制对双方同等适用——**"我以为推了"和"真的推了"是两件事**。

## 零之六、PM 推送自检规程（2026-10-18 新增）

**教训**：PM 自己也发生过漏推（commit 62fe820 声称推送但远端没有）。
git push 返回 0 不等于远端已更新。**双方适用同一条铁律：推完必验。**

### 强制规程

| # | 规则 |
|---|---|
| **P1** | PM 每次推送**必须**通过 scripts/pm/push_verified.py，不允许裸跑 git push |
| **P2** | 推送器会输出 5 行自检表（提交/推送/自检/差距/未推送提交），**必须全部 ✅** |
| **P3** | 自检不通过 → **不得对外声称"已更新"，不得让对端 pull 依赖本次内容** |
| **P4** | 向用户汇报推送时，必须附带自检结果（两个 hash + 是否一致） |
| **P5** | 对端同样适用：其每轮交付由 check_delivery.py 独立核查，不接受自报 |

### 标准用法

`ash
# 提交 + 推送 + 自检（一条命令）
python scripts\pm\push_verified.py -m "说明"

# 只自检（例如怀疑漏推时）
python scripts\pm\push_verified.py --verify-only
`

### 已抓到的三次漏推

| # | 对象 | 提交 | 发现方式 |
|---|---|---|---|
| 1 | 实现方 | cacd6be / 67fbc96 / 4540c0e | PM 用 cat-file 查 hash |
| 2 | **PM** | 62fe820（R2 任务书） | check_delivery.py 报 "本地有但远端无" |
| 3 | — | — | 机制建立后未再发生 |

> 两次漏推都是同一根因：**把"命令执行了"当成"结果达成了"**。
> 现在由脚本强制验 hash，不依赖人的记忆。

### ETF 轨道的验收标准（与个股策略不同）
| 指标 | 门槛 |
|---|---|
| 跑赢等权基准 | ≥3pp/年 |
| 夏普 | ≥0.7 |
| 最大回撤 | ≤25% |
| Calmar | ≥0.5 |
| 最大回撤持续 | ≤365 日 |
| 三段 holdout | 2016-20 / 2021-26 同号 |
| 成本敏感性 | 2× 成本后仍跑赢基准 ≥1pp |

### 关键设计差异（个股 vs ETF）
| 项 | 个股策略 | ETF 策略 |
|---|---|---|
| 印花税 | 卖出 0.05%（2023-08-28 后） | **免** |
| 往返成本 | 0.304~0.354% | **0.072%** |
| 容量 | ADV≥0.5 闸门，打掉一半超额 | 无约束 |
| 幸存者偏差 | 2016 前 8-9% | 归零 |
| 调仓频率 | 20 日 | **月频** |

> ⚠️ **不要把个股的 `config/costs.yaml` 用于 ETF**，必须单开一套。用 0.177% 卖出成本算 ETF 会把结论压死。

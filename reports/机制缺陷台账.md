# 机制缺陷台账（M 系列）

> 用途：记录**协作/验证机制本身**的缺陷（不是我的计算错误 E，也不是实现方的执行错误 I）。
> 用户 2026-10-18：「机制运行中出现问题，你要及时提出来，咱们再优化，我不认为可以一步到位。」
> 原则：**机制不是一次建成，是持续迭代。但每次迭代必须有台账编号，不许悄悄改。**

---

## 一、当前已识别的缺陷（PM 主动披露）

| # | 缺陷 | 严重度 | 现状 | 缓解手段 | 改进方向 |
|---|---|---|---|---|---|
| **M1** | **溯源闸只能验证"数字与 JSON 一致"，无法验证"JSON 是真实运行产物"** | 🔴 高 | 未解决 | ① PM 交叉验证（用原始曲线自算，已做过 corr=−0.1354）② 抽查复跑 | 让实现方在 JSON 内嵌**运行指纹**（数据文件 sha256 + 代码 sha256 + 参数 + 时间戳 + 行数），PM 抽查复跑比对 |
| **M2** | **预申报依赖实现方自觉"先写后跑"** | 🟡 中 | 未解决 | 申报文件有 git 提交时间戳，可事后核查 | 要求申报文件与 JSON **在同一次执行**中由脚本生成（申报时间必须早于 `generated_at`） |
| **M3** | **`check_delivery.py` 只查存在性/大小/关键词，不查内容正确性** | 🟡 中 | 部分缓解 | 有 `audit_citations.py` 补内容核对 | 把两者串成一条命令：交付校验通过后自动跑溯源校验 |
| **M4** | **门禁阈值仍由 PM 拍脑袋**（E2 夏普≥0.5、E3 候选池≥1500、E4 相关>0.80 全是这类） | 🔴 高 | 部分解决 | 已改相对标定 + 事前实测 | 建立**门槛标定规程**：任何绝对阈值必须先跑历史分布，证明它不违背市场容量/资产特性 |
| **M5** | **单一实现方，无第三方交叉验证** | 🟡 中 | 未解决 | PM 独立重算关键指标 | 关键结论由 PM 用**不同引擎**复算（如用 `portfolio_builder` vs 对方的 `strict_validate`） |
| **M7** | **G5'（超额集中度<60%）对条件型触发器天然不利** | 🟡 中 | 未解决 | 本轮按原规则收口，未调整 | 区分两类 alpha：①逐年型（应分散）②条件型（必然集中，如危机触发器）。条件型应改用「事件数 ≥N」而非「集中度」做样本量判据 || **M6** | **PM 的复核能力受限于自身算力/时间，抽查覆盖率低** | 🟡 中 | 未解决 | 优先抽查"结论性数字"（决定采纳与否的那几个） | 规定：每个结论必须至少有 **1 个数字被 PM 独立重算** |

## 二、登记格式

| 字段 | 说明 |
|---|---|
| 编号 | M<n>，单调递增 |
| 缺陷 | 具体是哪一环失效（不许写"机制不够好"） |
| 严重度 | 🔴 会放过错误结论 / 🟡 增加成本 / 🟢 体验问题 |
| 现状 | 未解决 / 部分缓解 / 已修复 |
| 缓解手段 | 当前用什么补 |
| 改进方向 | 下一版怎么做 |
| 发现方式 | PM 自查 / 实现方提出 / 运行中暴露 |

---

## 三、变更纪律

| # | 规则 |
|---|---|
| **M-A** | 机制可以改，但**必须先在台账登记**（编号 + 原因 + 影响面），不许静默修改 |
| **M-B** | 改完必须在看板 `§1.1 对齐记录` 留痕：改了哪条、为什么、什么时间 |
| **M-C** | 若某个机制连续 2 轮没有发现问题，**不等于它有效**，仍需抽查一次 |
| **M-D** | 用户提出机制问题 → 立即登记，并在下一轮给出改进方案（不许拖） |

# 研究知识库说明

> 目的：把 2026-10 那几天的全部研究（约 40 轮）沉淀成可查询、可重建、可交接的结构。
> 面向：本人 + 未来接手的 AI。

---

## 一、为什么分两个文件

| 文件 | 内容 | 是否入库 | 大小 |
|---|---|---|---|
| `data/cache/research_kb.db` | **全量**：结论层 + 行情层 | ❌ 本地（`.gitignore` 排除） | 4.86 MB |
| `data/kb/conclusions.sql` | **仅结论层** | ✅ 入 GitHub | 31.8 KB |
| `data/kb/conclusions.json` | 同上，JSON 版 | ✅ 入 GitHub | 32.4 KB |

**为什么行情层不能上 GitHub**：

`AGENTS.md` 规定「行情数据来自第三方（通达信/通联/CSMAR 等），**禁止再分发**；只开源代码 + 获取脚本 + 合成演示数据。」

所以：**结论是我们的成果，可以开源；行情是第三方的，不能。**

## 三、怎么用

### 3.1 查结论

```sql
-- 所有「已验证」的结论
SELECT fid, category, statement, evidence FROM finding WHERE verdict='CONFIRMED';

-- 所有「证伪」的信号（避免重复踩坑）
SELECT sid, name, rule, note FROM signal WHERE verdict='FALSIFIED';

-- 待办
SELECT oid, title, priority FROM open_item WHERE status='open' ORDER BY priority;

-- 我犯过的错
SELECT eid, edate, what, fix FROM error_log ORDER BY CAST(SUBSTR(eid,2) AS INT);
```

### 3.2 判定枚举

| verdict | 含义 | 使用规则 |
|---|---|---|
| `CONFIRMED` | ✅ 已验证 | 可写入策略 |
| `FALSIFIED` | ❌ 已证伪 | **禁止使用** |
| `PARTIAL` | 🟡 部分成立 | 只能轻用 |
| `REFERENCE` / `TEMPERATURE` | 📌 仅参考 | 不产生交易信号 |
| `USABLE` | ✅ 可用 | 唯一核心信号 |
| `LIGHT` | 🟡 可轻用 | 做轻度倾斜 |

## 四、怎么重建

### 4.1 从零重建全量库（需要行情数据）

```bash
python scripts/build_research_kb.py
```

从 `data/cache/dividend_research.db` 复制行情层，并写入全部结论。**幂等**，可反复跑。

### 4.2 只更新结论层（保留已有行情）

```bash
python scripts/build_research_kb.py --keep
```

### 4.3 导出结论层 + 重新生成文档

```bash
python scripts/export_kb.py
```

会生成：
- `data/kb/conclusions.sql`
- `data/kb/conclusions.json`
- `docs/研究结论总表.md`
- `docs/信号台账.md`

### 4.4 只有 `conclusions.sql` 时怎么恢复

```bash
sqlite3 research_kb.db < data/kb/conclusions.sql
```

然后跑 `build_research_kb.py --keep` 补行情层（或直接从源头重新抓）。

## 五、设计原则（为什么这么建）

| # | 原则 | 体现 |
|---|---|---|
| 1 | **证伪与有效同等留档** | `finding` 里 7 条 FALSIFIED、`signal` 里 9 条 FALSIFIED，不许只留成功的 |
| 2 | **结论必须带证据指针** | 每条 finding 有 `evidence`（量化数字）+ `data_pointer`（文件/表定位） |
| 3 | **错误必须入库** | `error_log` 15 条、`defect_log` 5 条，与结论并列 |
| 4 | **可重建** | 全库由脚本生成，不存在「只有库里才有」的信息 |
| 5 | **行情与结论分离** | 结论可开源，行情不可（合规） |
